1 Organisation of Submission:
•	MATLAB Code
Contains srrc_filter.m which is the MATLAB file involved in the design, simulation and verification of the SRRC filter.
•	Pre-AXI Transmit Chain Testing
This contains top_level.vhd. Prior to integration into the AD9361 reference design, most of the custom transmit chain was built and simulated in Vivado.  This ensures that the PRBS, modulation, framer and encoder works as expected in series. To do this, the design must be hierarchical with a top-level VHDL file defining the entity and Units Under Test. This file relates to the telecommand part chain (e.g PRBS -> Telecommand Framer -> BCH Encoder -> Modulation Mapper).  It intends to give an idea of the testing work carried out prior to the integration into the AD9361 reference design. 
•	Testbenches
Contains the testbenches for the BCH encoder, convolutional encoder, modulation mapper, PRBS23, symbol timer, telecommand framer and telemetry framer. A large proportion of this boilerplate code was written using ChatGPT 5.2. This was then adapted by the author. A testbench was always written for the intended IP core within the transmit chain (except for the SRRC filter). Testbenches were always used to ensure basic functionality (e.g whether the clock was running, whether resets worked etc) but also could be used to produce a simulation waveform that would give some idea of whether the IP core was meeting its specification (e.g ensuring correct modulation mapping).
•	VHDL
This is separated into two parts and represents the final code for every single custom IP block produced in Vivado. The are two types: AXI IP Cores and Non-AXI IP Cores. 

The AXI IP Cores folder contains the code for all five of the IP cores that contain an AXI4-Lite interface (and therefore can be configured by the user). They are: PRBS23, Modulation Mapper, Symbol Timer, Transmit Controller and SRRC Filter. Each of these blocks (apart from the Transmit Controller) is made up of three separate files: the top-level wrapper (which defines the external interface and instantiates the IP core), the AXI4-Lite slave interface wrapper (which handles all communication between the Processing System and the IP core) and finally the core logic module. The Transmit Controller merely reacts to user configuration via AXI and so does not have a core logic file. The top-level wrappers and the AXI4-Lite slave wrappers comes from a template generated by Vivado and then amended with the applicable registers and ports required.

The Non-AXI IP Cores consist of the remaining IP blocks without the AXI4-Lite interface. This includes both framer modules (telecommand and telemetry), both encoders (BCH and convolutional), the blocks required for correct path selection (e.g whether the telemetry and telecommand framing/encoding blocks need to be activated, and if so, which ones) and the mute multiplexer block. 
•	software_scripts 
These 4 Bash scripts are run within the Kuiper Linux environment:
-	.bashrc contains all of the commands that the user can utilise to configure the transmitter. This file was created by the OS but was empty originally. It is designed to store aliases.
-	fhss.sh contains the full script for the frequency hopping functionality. This use IIO to alter the transmit frequency of the AD9361. There are five different possible frequencies in the 2.4 GHz and 2.48 GHz range. 
-	rclocal.sh is the script that runs on Kuiper Linux and was used to initialise the transmitter. In this case it run the init_sdr.sh. 
-	sdr_init.sh is the file run to initialise the filter. It is an adapted version of an rc.local file that had been created by the OS. It ensures that DMA mode is selected (so the custom transmitter is the data source and not any internal DDS sources), any internal DDS tones are fully turned off, the sampling rate is set in software to 25 MSPS and the output frequency set to 2.4 GHz 
•   system_top.bit
The BOOT.BIN contains the AD9361 reference design within the custom transmit chain integrated into. It is created by using g the bootgen utility on the system_top.bit file. When stored on the SD card and inserted into the ZedBoard, the Kuiper Linux OS will boot and configure the FPGA with the implemented design.

3 Special Instructions to Run this Project on Digilent ZedBoard and Analog Devices AD9361 (Applicable to Ubuntu Computers)
1) Install Kuiper Linux onto an SD card with at least 16 GB of storage space (refer to https://wiki.analog.com/resources/tools-software/linux-software/kuiper-linux).
2) Ensure the ZedBoard is configured in SD card boot mode. Refer to the Digilent ZedBoard User Guide for assistance if required. There is a 5-position DIP switch that should be configured as 1-0-1-1-0.
3) Replace the BOOT.BIN file on the SD card with the BOOT.BIN file within this folder.
4) Insert the SD card into the Zedboard.
5) Turn the ZedBoard on.
6) Plug the computer into the UART port on the ZedBoard.
7) Run the command sudo minicom -D /dev/ttyACM0 -b 115200
   Note: Another port may be enumerated instead of ACM0. Run lsusb to check this. 
9) If a blank minicom terminal is displayed, restart the board.
10) Add the Bash scripts into the Kuiper Linux OS. Place them in the folder specified in the bash scripts themselves.
11) Source all of the added Bash scripts.
12) Restart the board.
